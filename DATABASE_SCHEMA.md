# D1 database specification

This is a schema design, not an applied migration. Add migration files only during implementation. The names below are authoritative across the design documents.

## Conventions and invariants

SQLite/D1 types: `TEXT`, `INTEGER`, `REAL`, `BLOB`. Application-generated UUIDs are TEXT primary keys unless a different key is specified. `!` means NOT NULL; `?` means nullable. All columns explicitly described below; abbreviations expand as follows:

- **ID** = `id TEXT PRIMARY KEY`.
- **OWNER** = `user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT CHECK(user_id='owner')`.
- **AUDIT** = `created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL` (UTC epoch milliseconds).
- **VERSION** = `version INTEGER NOT NULL DEFAULT 1 CHECK(version>=1)` for optimistic concurrency.
- **ENC** = one TEXT JSON envelope `{keyId,nonce,ciphertext}` using authenticated AES-GCM, validated by application and `json_valid`. Encryption material is never in D1.
- All booleans are INTEGER `CHECK(value IN (0,1))`; JSON fields have `CHECK(json_valid(column))` when non-null. Domain enum fields have CHECK constraints for their stated finite sets. Durations in seconds, distances in meters, power in watts, pace in seconds/km, percentages as 0–100+ documented units. Nonnegative quantities have CHECK ≥0. RPE 0–10, confidence 0–1.

The single owner is enforced by `users.id CHECK(id='owner')`; foreign keys plus this singleton prevent cross-owner references without pretending to be a multi-tenant schema. Queries still require the authenticated owner. A multi-user future requires an explicit migration to composite ownership constraints and authorization review.

FK deletion is RESTRICT unless stated; remove child records explicitly in purge jobs. Use CAS/version checks for mutable aggregates. Every FK used in joins/deletion has an index unless its PK/unique index already covers it. All calendar date columns validate `YYYY-MM-DD` shape in SQL and actual Gregorian validity in Zod. UTC timestamps are not local dates. External IDs are TEXT even when numeric-looking.

Use a composite FK `workouts(id,current_revision)` → `workout_revisions(workout_id,revision)` with `ON DELETE NO ACTION DEFERRABLE INITIALLY DEFERRED` to guarantee the current head exists; create initial workout + revision + steps in one D1 batch. This explicit exception to RESTRICT also allows a guarded purge to delete revisions then their workout within one batch. Test circular/deferred FK behavior in workerd before committing the first plan migration. A migration-compatible alternative is a validating trigger; do not leave an unchecked dangling head. Head revision must agree with calendar_date/sport/title projection, validated transactionally. Revisions cannot be updated after commit; an append-only trigger rejects UPDATE, and delete only occurs during explicit purge.

Structured AST validation: max nesting depth 4, ≤100 source nodes and ≤500 expanded leaves, no cycles, sibling positions contiguous; repeats have children and no leaf duration/target; leaves have no children. Require all repeats to be finite. `open` duration has no value and propagates unknown total. Distance steps require an explicit estimate or eligible pace target for estimated duration. Exact duration is the sum of timed leaves times repeat counts. Never convert distance to time using an invented athlete speed. Recovery repeats must represent whether the final recovery occurs explicitly; no implicit extra recovery. Multiple targets may be stored but adapter must reject combinations unsupported by Garmin.

## Transactions and concurrency

Do not assume `BEGIN` can span awaited D1 calls or a remote MCP call. Use one `DB.batch()` for local atomic multi-statement operations; official D1 docs specify rollback if a statement fails. A zero-row CAS update is not an SQL error, so it does not automatically roll back the batch.

Required guard pattern: make each mutation depend on the same immutable mutation UUID/revision and successful CAS, and force failed preconditions to abort the batch through a tested constraint/trigger. One concrete implementation choice is a `mutation_guards` table `(id TEXT PK, allowed INTEGER NOT NULL CHECK(allowed=1), created_at INTEGER NOT NULL)`: first insert `allowed=CASE WHEN all preconditions THEN 1 ELSE 0 END`; subsequent statements execute in that batch, then delete the guard. The insert fails on stale version, disabled owner, locked adaptation target, missing lease fence or wrong state. Guard rows must not survive success. Test the pattern in actual D1; never use JavaScript read/check followed by unguarded write. Schema migration adds this helper in Phase 1.

Zone and availability set edits guard/increment `athlete_profiles.version` as their shared aggregate version; their GET returns that version. Activity feedback/link/dedup mutations guard/increment `completed_activities.version` as well as any child version, so API If-Match refers to the activity aggregate. Connection and operation commands use state/fence guards; proposal commands use their explicit VERSION.

Atomic boundaries:

- Plan mutation: guard versions → insert immutable revision/steps/targets → update current projection → optionally enqueue an explicitly requested sync operation → record API idempotency and audit → remove guard.
- Suggestion approval: guard every target, unlocked state, plan mode, proposal expiry and input hash → append revisions → mark approved, all in one batch. Garmin delivery is a separate explicit action.
- Sync result: guard operation ownership/fence → retire old mapping and insert new mapping → operation terminal state/history, atomically. Never lose a returned replacement ID.
- Import page: upsert each source and canonical observation/revision → mark dirty analytics → commit the page checkpoint. Do not advance watermarks beyond persisted data. Chunk within binding/runtime limits, checkpoint only complete chunks.
- Lease claim: atomic conditional update/insert returning fence. Expired in-flight writes become ambiguous; fencing blocks stale local commits but cannot undo a remote side effect.
